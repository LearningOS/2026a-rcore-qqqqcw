# lab5：并发、同步与死锁检测

## 实现

每个 ProcessControlBlock 独立保存 DeadlockDetector。资源以 `(Mutex/Semaphore, id)` 区分，记录 Available、各线程的 Allocation 和当前未完成的 Request。创建资源和线程时扩展矩阵；退出线程不再被视作能够释放资源的参与者；回收线程号时清除旧请求，实际未释放的锁仍保持不可用。

锁定互斥量和 down 信号量前暂存请求，用 Work/Finish 寻找完成序列：若一个线程的所有 Request 不超过 Work，则假设它完成，Work 加上它的 Allocation。若无法完成所有存活线程，则撤销本次请求并返回 `-0xdead`，不修改真实等待队列或信号量计数。否则允许原有同步原语执行，实际获准后再将 Request 转为 Allocation。

unlock/up 更新记账并唤醒真实等待者。信号量允许未持有资源的线程执行 up；互斥量拒绝非持有线程的 unlock。即使关闭检测也持续记账，因此重新开启不会丢失此前持锁状态。开关仅接受 0/1，其他值返回 -1；同步对象编号和 waittid 做越界检查。

条件变量 wait 释放与重新获取互斥量时也同步更新记录，避免把等待条件变量的线程误认为仍持锁。所有任务切换前释放进程内部独占借用，防止新运行线程触发 RefCell 重入冲突。

并保留前章的页表与时间、内存映射、进程创建、文件硬链接与元数据实现。线程调度继续使用累计 stride。

## 原理与边界

死锁需要互斥、持有并等待、不可剥夺及循环等待同时存在。单实例资源可以使用等待图检查环；多实例信号量需要同时考虑可用数量与各线程已持有数量，不能简单把任何等待都视为死锁。这里依据当前请求做死锁检测，不要求用户提前声明最大资源需求，也不等同于完整银行家避免算法。

资源及线程状态属于进程，不能把相同编号的不同进程同步对象混为一谈。被拒绝的请求必须回滚，否则失败调用会在下一次检测中制造虚假的依赖。
